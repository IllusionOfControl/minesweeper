# Анализ проекта Minesweeper

> Дата анализа: 2026-06-18
> Версия: ветка `master` (commit `6543047`)

## 1. Описание проекта

Проект — настольная игра «Сапёр», написанная на **C++ (стандарт C++14)** с использованием
графического фреймворка **SFML 2.5.1** и системы сборки **CMake**.

### 1.1. Назначение

Классический «Сапёр»: поле из закрытых клеток, часть которых содержит мины. Игрок открывает
клетки левой кнопкой мыши, ставит флаги/вопросы правой кнопкой, цель — открыть все клетки без
мин. Поддерживаются:

- три предустановленных уровня сложности (Easy 9×9/10, Medium 16×16/40, Hard 32×16/99);
- пользовательский уровень сложности (ввод ширины, высоты и числа мин);
- таймер и счётчик оставшихся мин (LED-индикаторы);
- кнопка-смайлик со сменой реакции (обычный / нажатие / победа / проигрыш);
- меню (главное меню, меню сложности, экран «About»).

### 1.2. Архитектура

```
src/
├── main.cpp                  — точка входа, создаёт MineSweeper
├── MineSweeper.{cpp,hpp}     — корневой класс: главный цикл, загрузка ассетов, Context
├── DEFINITIONS.h             — макросы констант (размеры, битовые флаги клеток, сложности)
├── managers/
│   ├── AssetManager          — загрузка/хранение текстур и шрифтов (std::map по имени)
│   └── StateManager          — стек состояний (std::stack), переключение экранов
├── states/                   — экраны игры (паттерн «Состояние»)
│   ├── State.hpp             — абстрактный интерфейс (init/handleInput/update/draw)
│   ├── MainMenuState
│   ├── DifficultyMenuState
│   ├── CustomDifficultyState
│   ├── AboutState
│   └── GameState             — основная игровая логика
└── gui/                      — переиспользуемые виджеты
    ├── Component             — базовый класс (Drawable + Transformable)
    ├── Container             — композит виджетов
    ├── Button, SmileButton
    ├── Input                 — текстовое поле с фильтром/валидацией
    ├── Indicator             — LED-индикатор
    └── Background
```

Ключевые сущности:

- **`Context` (`GameDataRef = shared_ptr<Context>`)** — общий контейнер, прокидываемый во все
  состояния: окно `sf::RenderWindow`, `AssetManager`, `StateManager` и текущая сложность.
- **`StateManager`** — управляет стеком экранов; на каждом кадре `processStateChanges()`
  применяет отложенные добавление/удаление.
- **`GameState`** — содержит всю модель поля (`std::vector<int> mGridArray` с битовыми флагами
  на клетку) и отрисовку (`std::vector<sf::Sprite> mGridCells`).

### 1.3. Главный цикл

`MineSweeper::run()` в бесконечном цикле вызывает у активного состояния
`handleInput() → update() → draw()` без ограничения частоты кадров и без фиксированного шага
времени.

## 2. Проблемы проекта

### 2.1. Критические баги

#### B1. Провал (fall-through) в `switch` в `GameState::handleInput()` + чтение неверного члена union
Файл [GameState.cpp:96-181](../src/states/GameState.cpp#L96). В `switch (event.type)` **отсутствуют
`break`** между `case MouseMoved`, `case MouseButtonReleased` и `case MouseButtonPressed`. Из-за
этого:
- обработка отпускания кнопки **проваливается** в обработку нажатия;
- `MouseMoved` (пустое тело) проваливается в `MouseButtonReleased`;
- `break` есть только в конце `MouseButtonPressed`, а `KeyPressed` (сброс по `R`) тоже без `break`.

**Это не просто стилистическая проблема, а источник реального бага.** `sf::Event` — это `union`.
При событии `MouseMoved` активен член `event.mouseMove`, но код в ветке `MouseButtonReleased`
читает `event.mouseButton.button`, `event.mouseButton.x/y`
([GameState.cpp:104-105](../src/states/GameState.cpp#L104)) — **чужой член union**. Поле
`mouseButton.button` перекрывается с `mouseMove.x` (координата пикселя). Поэтому при движении мыши
к левому краю поля (`x == 0` → `sf::Mouse::Left`, `x == 1` → `sf::Mouse::Right`) обработчик может
**ложно «открыть» или «пометить» клетку без клика**. Логика держится «на честном слове» за счёт
внутренних проверок состояния, но при определённых координатах ломается.

#### B2. Неинициализированные поля → неопределённое поведение (UB)
- [StateManager.hpp:25-26](../src/managers/StateManager.hpp#L25): `bool _isRemoving;`,
  `bool _isAdding, _isReplacing;` не инициализируются в конструкторе. На первом кадре
  `processStateChanges()` читает мусорные значения — поведение зависит от компилятора/запуска.
- [GameState.hpp:71-75](../src/states/GameState.hpp#L71): `mNeedToUpdate`, `mCellsRevealed`,
  `mMinesCount`, `mGameTime` не инициализированы в списке инициализации конструктора.

#### B3. Рекурсивный «flood fill» без защиты от глубины
[GameState.cpp:284-316](../src/states/GameState.cpp#L284) — `revealCell` раскрывает соседей
рекурсивно. На больших полях это глубокая рекурсия (риск переполнения стека); следует заменить
на итеративный обход (очередь/стек).

#### B4. Пересоздание окна на каждом переходе экрана
Каждый `init()` состояния вызывает `mContext->window.create(...)`
([MainMenuState.cpp:10](../src/states/MainMenuState.cpp#L10),
[GameState.cpp:19](../src/states/GameState.cpp#L19) и т. д.). Это вызывает мерцание, теряет
позицию окна и дорого по ресурсам. Окно следует создавать один раз и менять размер/вид.

#### B5. Незащищённый `std::stoi`
[CustomDifficultyState.cpp:63](../src/states/CustomDifficultyState.cpp#L63) и далее — `std::stoi`
на строке ввода. Защищён только проверкой `isValid()`/непустой строки, но при изменении логики
валидации легко получить исключение `std::invalid_argument`/`std::out_of_range`, не
перехватываемое нигде.

### 2.2. Архитектурные проблемы

#### A1. Смешение логики и отрисовки в `GameState`
Признано самим автором в комментарии [GameState.cpp:7-10](../src/states/GameState.cpp#L7)
(«…everything is confused here :("). Модель поля, обработка ввода и рендеринг живут в одном
классе. Нет отдельного класса `Board`/`GameField` (он закомментирован в
[CMakeLists.txt:23](../CMakeLists.txt#L23)). Это мешает тестировать логику отдельно от UI.

#### A2. «Стек состояний», который не используется как стек
`StateManager` построен на `std::stack`, но все переходы делаются с `isReplacing = true`, методы
`Pause()`/`Resume()` закомментированы ([StateManager.cpp:24,40](../src/managers/StateManager.cpp#L24)).
Фактически это всегда «замена», стек избыточен; кнопка «назад» каждый раз создаёт **новый**
объект состояния вместо возврата к предыдущему.

#### A3. Захват по ссылке `[&]` в колбэках
Во всех состояниях колбэки кнопок объявлены как `[&]() { mContext->... }`
(например [MainMenuState.cpp:27](../src/states/MainMenuState.cpp#L27)). В методе класса `[&]`
неявно захватывает `this`. Пока состояние живо — работает, но это хрупко и неочевидно; корректнее
явный `[this]`. Любой рефакторинг времени жизни состояний легко превратит это в «висячую» ссылку.

#### A4. Дублирование кода в состояниях и виджетах
- Создание `mainMenuButton`/`exitButton`/фона повторяется почти дословно в четырёх состояниях.
- `Background` и `Indicator` дублируют boilerplate `isSelected/select/deselect/handleEvent`
  ([Background.cpp:25-39](../src/gui/Background.cpp#L25),
  [Indicator.cpp:32-46](../src/gui/Indicator.cpp#L32)).

### 2.3. Игровая логика (детальная проверка)

Помимо багов из §2.1, отдельная проверка игровых правил выявила следующее.

#### L1. «Мёртвое» условие в `updateGridCellsOnWin`
[GameState.cpp:362](../src/states/GameState.cpp#L362): условие
`mGridArray.at(i) == CELL_BOMB && (mGridArray.at(i) & CELL_FLAG)` **никогда не истинно**.
`== CELL_BOMB` означает значение ровно `0x9` (без флагов), а `& CELL_FLAG` (`0x10`) при этом всегда
`0`. Ветка нерабочая. Сейчас итог визуально корректен (следующая ветка всё равно ставит флажок всем
минам), но это логическая ошибка/недосмотр, который маскирует намерение.

#### L2. Безопасен только первый клик, но не его окрестность — *осознанное решение, не баг*
[initGridArray](../src/states/GameState.cpp#L250) исключает из расстановки мин **только саму**
кликнутую клетку (`cellNum == firstMoveCell`). Это **изначальная задумка**: гарантируется лишь то,
что первый клик не попадёт на мину (как в самой ранней версии Windows Minesweeper). Более поздняя
*де-факто* норма «первый клик открывает пустую область» (безопасны и 8 соседей) здесь сознательно
**не** реализована.

Поэтому L2 — не дефект, а зафиксированное проектное решение. Важный нюанс: расширять безопасность на
8 соседей в общем случае **нельзя** — при большом числе мин (`bomb_count > width*height - 9`) для
9 безопасных клеток попросту нет места. Если в будущем захочется «дружелюбного» старта, безопасность
соседей следует включать **опционально и только когда `bomb_count` это позволяет**, иначе откатываться
к гарантии одной клетки.

#### L3. Средняя кнопка мыши («аккорд» / chord) не работает — *запланировано к реализации*
«Аккорд» — классический приём быстрого открытия: если на открытой клетке с числом N уже выставлено
ровно N флагов вокруг, нажатие на эту цифру **разом открывает все оставшиеся непомеченные соседние
клетки**. [selectCellsArea](../src/states/GameState.cpp#L412) при нажатии средней кнопки лишь
визуально помечает 3×3 область флагом `CELL_SELECTED`, который тут же снимается в
[updateGridCells](../src/states/GameState.cpp#L402). **Самого открытия соседей не происходит** —
функция реализована наполовину (остался только зачаток визуального нажатия). Решено **реализовать**
её полностью (см. план).

#### L4. `reset()` не очищает модель поля
[reset](../src/states/GameState.cpp#L205) пересоздаёт только спрайты (`initGridCells`), но **не**
очищает `mGridArray`. Сейчас это безопасно, так как `initGridArray` пересоздаёт массив на первом
ходу, а до первого хода открытий нет. Однако зависимость неявная и хрупкая: при любом изменении
порядка вызовов в `mGridArray` останутся данные прошлой партии.

#### L5. Счётчик мин уходит в отрицательные значения с произвольным дном
[markCell](../src/states/GameState.cpp#L318) уменьшает `mMinesCount` при каждом флаге без проверки
остатка, а в обработчике ввода стоит магический предел `mMinesCount > -5`
([GameState.cpp:132](../src/states/GameState.cpp#L132)). В результате можно поставить флагов на 5
больше, чем мин, после чего постановка «молча» перестаёт работать. Поведение не объяснено и не
вынесено в константу.

#### Корректные места (проверено, багов нет)
- Расстановка ровно `bomb_count` мин с защитой от дублей и от первой клетки — корректна.
- Подсчёт чисел-соседей (`< CELL_BOMB` перед инкрементом) — корректен, коллизий со значением мины
  (`0x9`) нет, числа 0–8 умещаются в младший полубайт.
- Цикл пометок «нет → флаг → вопрос → нет» сохраняет баланс `mMinesCount`.
- Условие победы `width*height - mCellsRevealed == bomb_count` корректно, так как открыть мину
  означает мгновенный проигрыш (открытыми могут быть только безопасные клетки).
- Битовая упаковка `& 0xF` / флаги в старших битах непрозрачна (см. Q2), но согласована.

### 2.4. Качество кода

#### Q1. Непоследовательные соглашения об именовании
- Методы: `loadTexture` vs `LoadFont`, `getTexture` vs `GetFont`
  ([AssetManager.hpp:13-18](../src/managers/AssetManager.hpp#L13)).
- Префиксы полей: `mContext`, `_data`, `_isAdding`, `mNewState` — смешаны `m`/`_`/без префикса.

#### Q2. Макросы вместо типобезопасных констант
[DEFINITIONS.h](../src/DEFINITIONS.h) — всё через `#define`, включая:
- `#define DIFFICULTY_EASY {9, 9, 10, GAME_EASY};` с **точкой с запятой внутри макроса** —
  ловушка при использовании в выражении;
- флаги клеток (`CELL_FLAG 0x10` …) — следует сделать `enum`/`constexpr`;
- битовая упаковка значения и флагов в один `int` (`& 0xF`, `|= CELL_REVEALED`) непрозрачна.

#### Q3. Повторное определение `SQUARE_SIZE`
[SmileButton.cpp:3](../src/gui/SmileButton.cpp#L3) переопределяет `SQUARE_SIZE`, уже заданный в
`DEFINITIONS.h` — дублирование «магического числа».

#### Q4. `rand()` вместо `<random>`
[GameState.cpp:263-264](../src/states/GameState.cpp#L263) и `srand(time())`
([MineSweeper.cpp:12](../src/MineSweeper.cpp#L12)). Устаревший подход, плохое распределение,
не потокобезопасно.

#### Q5. Слабая обработка ошибок ассетов
`AssetManager::loadTexture` в одной перегрузке печатает в `std::cout`, в другой — молчит
([AssetManager.cpp:11,16](../src/managers/AssetManager.cpp#L11)). При отсутствии файла объект не
кладётся в map, а затем `getTexture` падает на `.at()` с необработанным исключением.

#### Q6. Мёртвый код и «магия»
- Закомментированный `GameField` ([CMakeLists.txt:23](../CMakeLists.txt#L23)),
  `Pause()/Resume()`.
- Неиспользуемое поле `Container::mSelectedChild` ([Container.hpp:25](../src/gui/Container.hpp#L25)).
- Магические числа позиций/смещений по всему GUI (например `mText.setPosition(0 + 20, 32 - 10)` с
  комментарием «magic numbers» [Input.cpp:16](../src/gui/Input.cpp#L16)).
- Магическая проверка `mMinesCount > -5` ([GameState.cpp:132](../src/states/GameState.cpp#L132)).
- `std::ceil(i / difficulty.field_width)` — `ceil` от целочисленного деления бесполезен
  ([GameState.cpp:237](../src/states/GameState.cpp#L237)).
- Дублирующая загрузка `tiles.png` под именами `option_buttons`/`background`
  ([MineSweeper.cpp:15-16](../src/MineSweeper.cpp#L15)).

#### Q7. Смешение языков в комментариях
Комментарии частично на русском, частично на английском
([GameState.cpp:142-143](../src/states/GameState.cpp#L142)).

### 2.5. Сборка и переносимость

#### C1. Проблемы `CMakeLists.txt`
- **Дублирующиеся** `find_package(SFML ...)` ([CMakeLists.txt:25,28](../CMakeLists.txt#L25)) с
  разными наборами компонентов.
- Запрашивается компонент `audio`, но линкуется `sfml-network` (а не `sfml-audio`), при этом
  `audio`/`network` в коде не используются.
- **Жёстко задан** `set(CMAKE_BUILD_TYPE Debug)` ([CMakeLists.txt:6](../CMakeLists.txt#L6)).
- Разделители пути с **обратными слешами** `\\_Resources\\`
  ([CMakeLists.txt:31](../CMakeLists.txt#L31)) — непереносимо на Linux/macOS.

#### C2. Относительные пути к ресурсам
Ассеты грузятся по относительному `_Resources/...`
([MineSweeper.cpp:13](../src/MineSweeper.cpp#L13)) — работает только если рабочая директория
совпадает с местом расположения ресурсов.

### 2.6. Тесты и документация

- **Полное отсутствие автоматических тестов** — нет ни одного теста для игровой логики
  (расстановка мин, flood fill, условие победы).
- `README.md` описывает только сборку/правила; нет описания внутренней архитектуры; в инструкции
  фигурирует placeholder-репозиторий `username/minesweeper`.
- Нет CI.

## 3. Как это можно исправить

| Проблема | Рекомендация |
|---|---|
| B1 — fall-through в `switch` + чтение чужого члена union | Расставить `break;` в каждом `case`; читать `event.mouseMove` в `MouseMoved` и `event.mouseButton` только в кнопочных событиях; вынести обработку нажатия/отпускания/движения в отдельные методы. |
| B2 — UB неинициализированных полей | Инициализировать все поля в списке инициализации либо через `= false;`/`{}` прямо в объявлении. |
| B3 — рекурсия flood fill | Заменить на итеративный обход с явной очередью `std::queue<sf::Vector2i>`. |
| B4 — пересоздание окна | Создавать окно один раз в `MineSweeper`; состояния меняют размер (`window.setSize`) и `sf::View`. |
| B5 — `std::stoi` | Обернуть в `try/catch` или использовать `std::from_chars`; централизовать парсинг ввода. |
| A1 — смешение логики/UI | Выделить класс `Board`/`GameField` с чистой логикой (без SFML), покрыть его тестами; `GameState` — только ввод+рендеринг. |
| L1 — мёртвое условие победы | Упростить `updateGridCellsOnWin`: помечать флажком все мины одной веткой; убрать недостижимое `== CELL_BOMB && & CELL_FLAG`. |
| L2 — безопасность первого клика | Оставить как есть (осознанное решение — безопасна одна клетка); задокументировать. Опционально: расширять безопасность на соседей, только когда `bomb_count <= width*height - 9`. |
| L3 — нерабочий «аккорд» | **Реализовать** chord: при нажатии на открытую цифру с верным числом флагов открывать оставшихся непомеченных соседей (с проигрышем, если флаг стоит неверно). |
| L4 — `reset()` не чистит модель | Очищать `mGridArray`/счётчики в `reset()`, не полагаясь на отложенную переинициализацию. |
| L5 — отрицательный счётчик мин | Вынести правило в именованную константу или запрещать ставить флагов больше, чем мин. |
| A2 — стек состояний | Либо реализовать полноценный push/pop с Pause/Resume, либо упростить до явной «замены экрана». |
| A3 — `[&]` колбэки | Заменить на явный `[this]`; вынести построение типовых кнопок в фабрику. |
| A4 / Q6 — дублирование, мёртвый код | Вынести общий код кнопок «меню/выход/фон» в helper; удалить неиспользуемые поля и закомментированный код; добавить общий базовый класс для «статичных» виджетов. |
| Q1 — нейминг | Привести к единому стилю (`camelCase` методы, `m`-префикс полей); переименовать `_data`. |
